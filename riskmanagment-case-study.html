CASE STUDY
RISK & COMPLIANCE PLATFORM

Turning a generic admin template into a bank-grade risk platform

Risk management platform helps financial institutions gather and reconcile data, then calculate, aggregate and report regulatory credit, market, operational and concentration risk - in a natively integrated, modular environment. The product's UI was built on AdminLTE, a free general-purpose dashboard template. My job was the style guide, information architecture and UX decisions that turn that template into something bank back-office users can work in all day.

01 · RESEARCH

Learning a domain I wasn't trained in, and auditing what I inherited

Before any pixels: COREP, IRB vs. standardised approaches, XBRL taxonomies, and what "exposure," "obligor" and "concentration risk" actually mean. I couldn't design a status model for an approval chain without understanding what a change request is in a regulated bank, or why an audit trail is non-negotiable.

I worked through the product's existing data model and the regulatory vocabulary with engineering and product, then mapped the terms users would see on screen against the terms the database used the two didn't always match, and where they didn't, the screen had to win.

These screens were created new rather than inherited, so design decisions were being made while development was already moving. Without a shared style guide, every new module risked inventing its own buttons, table and status treatment.

Context, constraints, goal The product spans four risk domains and multiple approaches credit, market, operational and concentration risk, standardised through IRB. A platform growing in this many directions can't be designed screen-by-screen, it needs a system underneath it. The goal wasn't to simplify what a risk officer sees an inherently dense, high-stakes dataset but to make it scannable and trustworthy.

Auditing the template I was handed

AdminLTE is built to demo a bit of everything: widgets, chat panels, social cards, calendars. Risk management platform needs COREP reporting, exposure reconciliation, XBRL validation and an approval chain almost nothing in the stock template maps to that. I went through every component and sorted it into four buckets, which became the brief for everything after.

KeepSidebar shell, box/panel pattern, data tables, breadcrumbs, paginator
AdaptButtons, badges/labels, modals, form controls, date picker
DropChat widgets, social cards, to-do lists, timeline feeds, stock calendar
Build newStatus badges, import result log, approval queue, criteria-selection dialog, KPI cards, tasks/notifications dropdowns

02 · SKETCHING & WIREFRAMING

Restructuring the navigation, then mapping the two flows that carry the product

The early menu mirrored the system's internal structure. Everything flat under Admin and Data Management, with related tasks scattered. I regrouped the sidebar around what people come to do: administering the platform, moving data in and out, and moving changes through the approval chain. Approvals became its own group rather than sitting inside Admin, because it's a distinct job done by distinct people.

Two task flows account for most daily use: import → validate → review errors → reconcile, and submit change → route for approval → approve or reject → audit record. I wireframed both at low fidelity before touching any styling, to test where a decision gets made versus where the interface makes you go to make it.

Moment of conflict In the original flow, every single request routine or not, opened a modal to resolve. For a queue of thirteen, that's thirteen open-read-decide-close cycles. The wireframe made the cost visible before anything was built.
UX decision Resolve routine approvals inline on the row, keep the full dialog for anything needing a comment or audit reason. The dialog stops being the only door, it becomes the door for consequential decisions.

03 · PROTOTYPING & ITERATION

A three-tier token system, so the platform can grow into it

Rather than restyling screens one at a time, I extracted every color already in the product's CSS, deduplicated it, and rebuilt it as ramps with fixed semantic meaning: primitives (raw ramps), semantic (roles like color-action-danger), and component (specific usages like button.primary.background). This is what makes the light/dark sidebar work without duplication — both skins read the same semantic tokens, so a new nav item or state is styled once.

04 · OUTCOMES & LESSONS LEARNED

What the system delivers

A real Dashboard, not an empty menu item. Pending approvals, import health, record counts and exposure breakdown are visible on login, instead of living only inside each sub-screen.
Approve / reject without leaving the table. Routine change requests resolve inline; the full dialog stays for anything needing a comment or audit reason.
One shell, two skins, zero drift. Light and dark sidebar are the same markup reading different token values, so a new nav item or state never has to be styled twice.
Status has exactly five colors, everywhere. Success, warning, alert, info and neutral mean the same thing whether you're in an import log, an approval queue, or a badge.
A system the platform can grow into. New modules across credit, market, operational and concentration risk inherit the tokens and components instead of inventing their own.

What I'd do differently

Honest notes, because a case study without them isn't worth much.

Validate with real users earlier. These decisions were grounded in domain research, stakeholder input and established patterns for dense back-office tools - not in moderated testing with bank risk officers. The inline-approval change in particular is the kind of thing I'd want to watch someone use before calling it settled.
Build the token system before the first screen, not alongside it. Tokens were extracted from CSS that already existed, so I was reconciling decisions that had already shipped. Starting from the system would have been cleaner - though in a project already in development, working in parallel was the realistic option.
Push further on the widest tables. A 752-row, many-column exposures grid deserves its own dedicated pass: saved filter sets, column presets per role, and a considered approach to horizontal scroll.
